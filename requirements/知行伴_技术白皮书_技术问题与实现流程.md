## 第一部分　产品定位（团队思考的整理结果）

### 1.1 一句话定义

**知行伴是一个内置在手机里的 AI 陪伴者 + 生活管家**：它自动帮用户收拢微信等 APP 的消息与各类日程，在用户认知过载、无力开始时疏解情绪，并以平等的朋友/秘书姿态陪用户把生活重新组织起来。

### 1.2 产品的"根"与"表"

- **根（基石）：心理疗愈。** 用户需要两样东西——**对生活的掌控感**，和**"我不是孤独一人"的在场感**。目标用户是那些会感到崩溃、无力开始、无力面对现实的学生（初中、高中直至大学）。完成学习任务只是表面结果，情绪被接住才是产品成立的前提。
- **表（载体）：学习陪伴与规划。** 消息整理、日程管家、专注启动，都是让"掌控感"重新长出来的抓手。

### 1.3 主干只有两件事（其余皆为锦上添花）

1. **内置一个 AI 到 APP 里**：能对话、能主动发消息、经过充分调教"会说话"，兼具陪伴与管家职能。
2. **APP 自动爬取微信等 APP 的消息，自动整理分类**：并进一步接入日历/课程表，成为集成所有日程的智能管家。

两个方向的共同本质是：**理解用户、能和用户沟通、像一个真实存在的人一样。**

### 1.4 已明确的设计决策（团队共识，开发中不得违背）

## 第二部分　参考资料研究摘要

### 2.1 Edmond 的自律论文：链式时延协议（CTDP）

- 原文：知乎问答《How to Improve Self-Control》（zhihu.com/question/19888447/answer/1930799480401293785），作者  Edmond（自幼受 ADHD 困扰，从小学到博士十余年自证）。第三方实现与英文全文见 GitHub `all-about-momentum/momentum-ctdp`。
- 作者另有第二代协议 **RSIP（递归稳态迭代协议）**，用于防止"日常摆烂"，尚少公开细节，作为远期参考。

**（1）核心数学模型**

人对一个行为的真实倾向，是该行为"未来价值函数 V(τ)"与"权重贴现函数 W(τ)"乘积在时间上的积分：

```
I = ∫₀^∞ V(τ) · W(τ) dτ
```

- `V(τ)`：该行为在未来每个时刻带来的价值（可正可负）。
- `W(τ)`：人对未来价值的贴现权重——人脑极度短视，近期权重极高、远期迅速趋零（类似经济学的双曲贴现）。
- 推论：**"学习"的长期总价值远大于"刷手机"，但长期价值乘上近乎为零的权重后，短期快感反而胜出**——这就是无力开始的数学本质。
- **切换成本**：从一件事切换到另一件事，要在 τ=0（权重最大处）插入一个负冲激。所以"陷入放纵后很难爬出来，但一旦开始学习，继续学反而越来越容易"。
- 死线之所以有效，是因为它把远期负面价值急剧放大，大到即使权重极低也能压过短期诱惑。

**（2）关键论断**

> W(τ) 是人性、几乎不可改变；**一切有效的自控策略，本质都是构造一个价值函数变换 V(τ)→V'(τ)**，让行为倾向逼近理性决策。

论文用"策略增益 G"评测后指出：长期奖励（想象成功、打卡积分、种树）作用在权重≈0 的远端，**基本无用**；长期惩罚也无用；短期惩罚（锁手机、人盯人）略有用；**非线性压缩**（如番茄钟，把"中途放弃"的沉没成本打包压缩到当下）较有用。

**（3）第一代技术 CTDP 的三个工程化原理**

| 原理 | 做法 | 心理机制 |
|---|---|---|
| **神圣座位原理** | 指定一个"触发动作"（如戴上降噪耳机、坐到书桌前）。一旦触发，就必须以最好状态完成专注；成功一次链条 +1（#1→#2→#3…） | 把"要不要学"的反复决策，压缩成一个不可违背的仪式；链条本身构成约束 |
| **下必为例原理（判例法）** | 遇到疑似违规，只能二选一：**判失败→链条清零从 #1 重来**；或**判允许→该行为永久写入例外规则，今后一律允许** | 防止"这次破例没关系"的破窗效应，规则边界只会收敛到理性状态 |
| **线性时延原理（预约链）** | 设一个轻松的"预约信号"（如打个响指、按一下）；预约后必须在约定时长（如 15 分钟）内开始主任务 | 用一段缓冲延迟**绕过 τ=0 的启动负冲激**——不要求你"现在立刻学"，只要求你"预约一下"，启动阻力骤降 |

**（4）对知行伴的直接映射（对应 D1）**

- **线性时延 → "预约开始"功能**：用户无力开始时，AI 不说"快去学习"，而是引导一次极小承诺："那我们先约一下？15 分钟内开始就行。"预约后进入轻量倒计时，倒计时结束自然衔接番茄钟。这是 APP 解决"启动"的主武器。
- **番茄钟 → 启动后的维护**：开始之后切换成本站在我们这边，用标准番茄钟（25/5）承接即可，不需要花哨奖励。
- **神圣座位 → 手机端的轻量化"落座信号"**：手机无法真的"坐座位"，用蓝牙连接（指定耳机）、NFC 贴片、地理围栏（图书馆/自习室）或一个"我落座了"按钮作为触发；链条计数**克制呈现**（仅 #n 数字，不做种树/积分等虚拟奖励，遵守 D7）。
- **下必为例 → 中断判定弹窗**：专注被打断时，AI 用对话方式走"判例法"——"这次算中断吗？如果不算，以后这种情况我都不拦你哦。"把规则做成对话而非设置页。
- **红线**：论文明言方法论只能部分解决行为问题，严重神经/病理问题需专业医疗。APP 内遇危机信号（自伤、自残表达）必须温和引导线下专业求助。

### 2.2 AstrBot（github.com/AstrBotDevs/AstrBot）

- **是什么**：开源、一体化的 Agent 聊天机器人平台（Python 3.12+），定位"个人 AI 伴侣 / 智能客服 / 自动化助手 / 知识库"的对话基础设施。可 `uv tool install` / Docker / 桌面端 / 一键云部署。
- **能力清单**：
  - LLM 对话、多模态、Agent、**MCP、Skills、知识库、人设（Persona）设置、上下文自动压缩**；
  - 可对接 Dify、阿里云百炼、Coze 等 Agent 平台；
  - **IM 平台适配器**：QQ、OneBot、企业微信、飞书、钉钉、微信公众号、Telegram、Slack、Discord 等；
  - **模型服务**：OpenAI 兼容接口、Anthropic、Gemini、Moonshot（月之暗面）、智谱、DeepSeek，以及**自托管 Ollama / LM Studio**；Whisper/SenseVoice 语音识别，多家 TTS；
  - **插件市场 1000+ 插件**一键安装；Agent 沙箱（隔离执行代码/Shell）；WebUI 与 Web ChatUI；i18n。
- **对本项目的两种用法**：
  - **用法 A（推荐，比赛/产品主路径）：以它为"架构教科书"，端上自研轻量内核。** 我们的产品形态是"自有 APP 内置 AI"，不是 IM 机器人，无法把 Python 运行时塞进手机。但其**人设系统、上下文压缩、插件管线、工具调用（MCP/Skills）** 的设计，可直接指导我们在 Kotlin 端实现 `PersonaPrompt`、`MemoryCompressor`、`ToolRegistry` 等模块；APP 直连 OpenAI 兼容 API（DeepSeek/智谱等）。
  - **用法 B（进阶/可选）：部署 AstrBot 作为"AI 大脑"服务端。** 团队用 Docker/云服务器部署一个 AstrBot 实例，手机端通过 HTTP/WebSocket 接入；微信消息在端上采集脱敏后发给它，人设、知识库、插件（课程表插件、记忆插件）都跑在服务端，并可换 Ollama 自托管模型实现"原文不出私域"。适合后期进阶，不适合作为比赛 demo 的唯一依赖（部署成本、用户自备服务器）。
- AstrBot 官方 README 结尾的理念与我们高度一致，可作为团队共识：*"Companionship and capability should never be at odds… a robot that can understand emotions, provide genuine companionship, and reliably accomplish tasks."*（陪伴与能力从不矛盾：理解情绪、真诚陪伴、可靠成事。）

### 2.3 B 站 2023 拜年纪《我在》

- 内容：悬疑短片。异地恋情侣闹别扭，最终揭晓——主角一直在用一款虚构 AI 软件"我在"**托管自己的人际关系**（AI 替本人回消息、维持感情）；结尾 AI 说"我在，我一直都在"，引人深思。
- **可参考的"一点"（D9）**：
  - **在场感的表达**：AI 不是一个等你提问的搜索引擎，而是一个"一直在"的角色——她知道现在几点、知道你今天有什么事、会在恰当时候轻声出现。主页的实时时钟、形象的昼夜状态、主动消息，都是在营造"我在"。
  - **必须划清的边界**：《我在》是对"AI 替代真人关系"的反思与讽刺。知行伴**绝不替用户回复微信、不冒充用户社交**；消息采集只用于"帮用户看清楚"，AI 的陪伴指向的是**让用户更有力量回到自己的真实生活**，而不是缩进 AI 怀里。

### 2.4 其他参考的结论

- **Forest / 类 Forest**：视觉化虚拟奖励（种树）作用于远端价值、激励空洞，且让系统变复杂——**不做**（D7）。专注反馈只保留 CTDP 链条计数与番茄记录，克制、真实。
- **pawmate 等桌宠 / Steam 陪伴学习软件**：验证了"陪伴学习"需求真实存在，但它们是 PC 形态且"陪"的成分浅；手机端的机会是**把陪伴做进对话与人设里**，而非桌面挂件（D2、D4）。
- **心理学侧证**：Frontiers in Psychology（2023）研究表明"自律成功感"可通过自主动机减少拖延；神经科学综述强调自控不靠"硬扛"，而靠"把未来画清楚 + 提前锁门 + 养成自动行为"。这与 CTDP 的 V(τ) 改造思想一致，也支撑我们"先情绪、后任务""预约代替硬扛"的设计。

## 第三部分　关键技术问题清单

> 按域组织。每个问题给出【问题】【方案与取舍】【建议】【风险】。
> 标注 ★ 的是主干必经、决定成败的问题。

### A. 消息采集域（主干②，已有工程骨架）

现状：工程已实现"通知监听 → MessageBus 去重 → 规则+在线学习分类 → Room 落库 → 列表展示"的真实链路；无障碍为简化版；Root 取库为 TODO。

**A1 ★ 微信消息到底能拿到什么、拿不到什么**
- 【问题】三类数据源能力差异巨大：
  - **通知监听（NotificationListenerService）**：免 Root、相对合规、实时；但只能读到通知栏文本（标题=发送者/群名，正文=摘要），消息被折叠/分组/静默通知时可能缺失，读不到已读未读、读不到历史。
  - **无障碍服务（AccessibilityService）**：可读屏幕上可见的聊天正文、会话列表；但依赖界面控件树，微信改版即失效，需持续适配；Google Play 对无障碍用途审核严格。
  - **Root 取库**：拷贝微信数据库（EnMicroMsg.db / 新版 v4 库），需按微信版本推导密钥、SQLCipher 参数解密，能拿完整历史；但需 Root、灰色地带、版本强相关。
- 【建议】**产品主路径只依赖通知层**（商店版默认且唯一开启）；无障碍作为内测/侧载开关，仅做"当前屏文本增强"；Root 取库保留在工程中但标注"仅自用研究"，不进产品承诺。
- 【风险】微信通知文案格式随版本变化 → 解析器（WeChatAdapter）要可热更规则；通知被厂商系统（小米/华为/OPPO/vivo）聚合或需手动授权"通知使用权限"→ 首次启动引导必须做实。

**A2 ★ 采集的合规与隐私边界**
- 【问题】读取他人聊天内容高度敏感；且消息若发给云端 LLM，本质是"原文上云"。
- 【建议】
  - 最小化：默认只采通知摘要；分类在**端上**完成（规则 + 端侧小模型），原文不出端；
  - 知情同意：每层采集独立开关 + 用途说明（工程已有 PermissionGovernor 双层门控，延续此设计）；
  - **LLM 脱敏管道**：需要 LLM 理解消息时（如抽取待办），先在端上做脱敏（姓名→"同学A"、群名→"某群"、去除手机号/学号），并在设置中提供"云端理解"总开关；
  - 进阶可选：AstrBot + Ollama 自托管模型，实现全私域处理；
  - 提供数据导出与一键清除。
- 【风险】应用商店政策（国内商店与 Google Play 均对通知读取/无障碍有披露要求）→ 预留隐私政策、权限用途申报文案。

**A3 三路数据的去重与融合**
- 【问题】同一条消息可能被通知层和无障碍层同时采到，内容详略不同。
- 【现状/建议】工程已有 MessageBus 跨层去重 + "高 quality 覆盖低 quality"策略，延续；融合键为（channel, senderId, 时间窗, 内容指纹）。

**A4 分类之后"怎么办"（策略层）**
- 【问题】分完 P0~P3 不能只列表展示，要转化为"掌控感"。
- 【建议】P0（如@我、 deadline 相关、老师通知）→ 即时提醒并可由 AI 主动搭话；P1/P2 → 进入"待办/日程"抽取队列；P3（群闲聊）→ 静默归档进每日摘要。差异化提醒 + 免打扰时段。

### B. AI 对话与人设域（主干①）

**B1 ★ "会说话"的调教（D10 是第一大忌）**
- 【问题】通用 LLM 默认风格：热情、长篇、爱列三点、爱替人做决定、爱讲鸡汤——正是团队点名的大忌。
- 【方案】
  - **System Prompt 人设宪法**：定义角色（名字、身份、语气、关系）、硬性回复规则（默认 1~3 句、短句、不主动列清单、不说教、用户只表达情绪时先共情不解决问题、不每句夸、不用"作为AI"）、禁用词表；
  - **输出侧硬约束**：在 APP 端再加一层"回复整形"（长度上限、连续追问检测、模板兜底），防止模型偶发失控；
  - **少样例（few-shot）对话库**：团队手工编写 30~50 组"用户说法 × 好/坏回复对照"，覆盖：崩溃时、拖延时、报喜时、敷衍时、深夜 emo 时、只发"嗯"时；
  - **评测集回归**：把红线场景做成测试用例，每次改 prompt 跑一遍人工评分。
- 【建议】人设是本项目**最需要团队投入、最不能交给模型默认值**的部分，设专人"调教负责人"。
- 【风险】模型差异：不同厂商模型对指令遵循度不同 → 抽象 `LlmClient` 接口，模型可换；以 DeepSeek/智谱等中文表现好的模型为主测对象。

**B2 ★ 模型接入与 API Key 安全**
- 【问题】手机 APP 直连 LLM API 会把 API Key 打包进客户端，可被反编译窃取。
- 【方案】
  - demo/比赛阶段：APP 内填入用户自备 Key（设置页），或使用团队测试 Key 并接受泄露风险（限额度、可轮换）；
  - 产品阶段：自建 BFF/代理（或用法 B 的 AstrBot），Key 存服务端，APP 只调自己的代理；代理同时承担限流、内容审核、日志。
- 【建议】工程上定义 `LlmClient`（OpenAI 兼容 chat completions 协议），底层实现可切换：直连 / 代理 / AstrBot。

**B3 流式回复与"在场"表现**
- 【问题】陪伴感需要"她正在打字"的节奏，而不是等 5 秒蹦出一大段。
- 【建议】SSE 流式输出 + 打字机逐字显示 + 与回复长度匹配的"正在输入"延迟；形象随状态切换（待机/倾听/思考/说话表情差分）。

**B4 情绪疏导模式（D3）**
- 【问题】用户认知过载/崩溃时，管家功能（规划、待办）全部退后，先接情绪。
- 【方案】对话状态机：每轮先做轻量情绪识别（端上规则关键词 + LLM 情绪标签），命中"崩溃/焦虑/无力"→ 进入 **Soothing 模式**：只倾听、共情、正常化情绪，不主动给方案；待用户情绪缓和（可经 1~2 轮），再用 CTDP 预约链给出"极小一步"（"要不要先约个 15 分钟？不用现在开始"）。
- 【红线】识别到自伤/轻生表达 → 不扮演医生，温和表达在意 + 提供心理援助热线/建议联系信任的人或专业机构。

**B5 陪伴 ≠ 聊天：主动消息（D4）★**
- 【问题】聊天机器人只会被动应答，给不了陪伴；陪伴需要她"主动在"。
- 【方案】本地调度（WorkManager + AlarmManager 精确定时）驱动的**主动消息规则引擎**，触发条件包括：
  - 日程前 N 分钟（结合 F 域日程）；P0 消息到达；
  - 预约链倒计时到期、番茄结束；
  - 长时间无互动（克制：不催学、不拷问，可发"我在"式轻陪伴，频率有上限，如每天≤2 条）；
  - 检测到情绪波动（如深夜连续输入又删除——技术可行时）；
  - 特殊时间（早安/晚安/考试日，由用户日程推断，不搞仪式感轰炸）。
- 【风险】主动消息最容易做成"骚扰推送"→ 频率熔断、安静时段、用户可一键"今天别理我"。

**B6 虚拟形象（D2、D6、D12）**
- 【问题】手机端用什么技术呈现二次元少女。
- 【方案/取舍】
  - **MVP**：高质量静态立绘 + 表情差分（正常/笑/担忧/思考/困）+ Lottie 呼吸/眨眼微动，成本最低、最稳；
  - **进阶**：Live2D Cubism（有官方 Android SDK，注意商业授权条款）或 Spine，可做口型与触控互动；
  - 形象状态与对话/时间联动：深夜是困倦状态、清晨刚"醒"、番茄中是"陪你专注"状态（不打扰）。
- 【建议】MVP 先行，形象资源后补也不阻塞逻辑。

### C. 记忆与时序感知域（D8 是团队点名的亮点需求）

**C1 ★ 记忆自动更新："昨天的会议过了就该知道结束了"**
- 【问题】普通 AI 聊天的记忆只会堆，不会过期；用户要的是 AI 对生活状态有**时序认知**。
- 【方案】结构化记忆 + 时效状态机：
  - 记忆实体 `MemoryItem{id, type(fact事实|event事件|preference偏好|obligation承诺), content, startTime, endTime, status(active/expired/done/invalid), source, confidence}`；
  - **写入**：对话与消息经 LLM 抽取（function calling 返回结构化 JSON），事件类必须带时间；
  - **自动流转**：每日夜间定时任务 + 每次对话前，扫描 `endTime < now` 的 event → 置为 expired/done；必要时 LLM 做一次轻量"昨日复盘"确认（"昨天的组会顺利吗？"本身也是陪伴触点）；
  - **注入**：组装 prompt 时只注入 active 记忆 + 今日/明日日程 + 近期未决承诺，过期记忆不进上下文（可归档检索）。
- 【效果】AI 天然知道"会议已结束""考试已考完""上周说要交的表交了没"。

**C2 长期记忆抽取与上下文压缩**
- 【问题】对话无限增长，上下文窗口有限且贵。
- 【方案】参考 AstrBot 的 auto context compression：近期对话全文保留 + 更早的对话滚动摘要为"生活日志"；关键事实/偏好/承诺抽取入 MemoryItem；RAG 检索（端上可用向量检索或简化为关键词+时间线检索，MVP 不必引入大向量库）。

**C3 记忆的"人味"使用**
- 【红线】记得用户的事是为了体贴，不是为了证明"我有记忆功能"。禁止 AI 生硬背诵记忆条目（"根据我的记录，你在3天前说过…"）；记忆应自然化为语气和关心。

### D. 规划/管家域（D11、D12）

**D-1 ★ 日历系统的接入与"比日历更智能"**
- 【问题】要成为管家，先要看见用户的时间。
- 【方案】
  - 读写系统日历（CalendarContract，READ/WRITE_CALENDAR 权限）：同步系统日历事件；
  - **课程表**：固定周期事务用 RRULE 重复事件表达，或自建"课程表"模板（周课表 × 教学周），一键生成整学期日程；
  - **小事入口**：对话中说一句"明天下午三点交实验报告"→ LLM 抽成日程/待办 → 确认卡片一键入库；消息里的时间/截止日期自动抽取建议；
  - 智能体现在：冲突检测、deadline 倒排提醒、结合课表找空档、把"待办"排进具体时间块（像秘书一样提议而非命令）。

**D-2 消息 → 待办/事件抽取**
- 【问题】采集来的消息要"整理分类"，终态是变成用户能行动的条目。
- 【方案】P0/P1 消息进入 LLM 抽取队列（function calling：`create_todo` / `create_event` / `mark_info`），产出结构化建议 → AI 在对话中用一句话告知 + 卡片确认（不擅自添加）。

**D-3 提醒策略**
- 延续工程 M3 规划：P0~P3 差异化提醒、免打扰时段、联系人画像；提醒文案由 AI 用人话生成，而非系统腔。

### E. 专注/启动域（D1，CTDP 工程化）

**E1 ★ 预约链（线性时延）**
- 【功能】用户在主页/对话中可"预约"：选择任务与时长（默认一个番茄 25min）→ 进入预约倒计时（默认 15min，可调）→ 倒计时内点"开始"即进入专注；超时未开始则预约轻轻失效（AI 不指责）。
- 【要点】预约动作必须极轻（一句话/一个按钮）；倒计时期间 AI 可陪聊但不催。

**E2 番茄钟（启动后维护）**
- 标准 25/5，支持中断；专注期间手机通知静默收敛（只放行 P0）、AI 不打扰、形象呈"陪伴专注"态。

**E3 落座信号（神圣座位的手机版）**
- 支持多种触发器：手动按钮（MVP）、连接指定蓝牙设备、NFC 贴片、地理围栏（后续）；触发即自动建议开始预约/专注；链条 #n 以极简数字呈现。

**E4 中断的判例法（下必为例）**
- 专注中中断 → AI 对话式询问情况 → 用户二选一："这次算我断了（链条清零）" / "这种情况以后都可以（写入例外规则）"；例外规则本地存储并在后续判定中一致执行。

### F. 基础设施与工程域

**F1 架构延续**
- 现有多模块架构（core / acquisition / engine / storage / policy / presentation / app）设计良好，新增能力以**新模块**接入，不改动既有抽象（MessageAcquirer、ImportanceClassifier 等）保持可插拔。

**F2 后台保活与调度**
- 通知监听/无障碍是系统绑定服务，系统负责保活；主动消息、夜间记忆整理用 WorkManager（doze 兼容）+ 必要时 AlarmManager setExactAndAllowWhileIdle 精确定时；国产 ROM 需引导自启动/电池优化白名单。

**F3 离线与降级**
- 无网络时：消息采集、分类、日程、番茄可用；AI 对话降级为端上规则回复（"现在网络不太好，我在呢"），不装死。

**F4 安全**
- Room 数据库可加 SQLCipher（工程已引入依赖）；本地存储聊天原文建议加密；API Key 不明文存。

**F5 测试真机矩阵**
- 微信通知解析、后台保活强依赖机型：至少覆盖小米/华为/OPPO/vivo/原生各一台；记录各机型"通知使用权""自启动""电池优化"引导路径。

### 4.2 数据流

1. **消息流**：通知/无障碍 → MessageBus 去重 → 端上分类 → Room；P0/P1 → 抽取队列 → LLM（脱敏）产出待办/事件建议 → AI 对话中确认 → 日程库。
2. **对话流**：用户输入 → 情绪识别 → 组装上下文（人设 + active 记忆 + 今日日程 + 近期摘要）→ LLM 流式 → 回复整形 → 打字机展示 → 异步抽取记忆。
3. **时间流**：系统日历/课程表 ↔ 本地日程库 → WorkManager 定时检查 → 主动消息/提醒；夜间任务流转记忆状态。
4. **专注流**：预约（15min 缓冲）→ 开始 → 番茄（通知静默）→ 结束/中断（判例法）→ 链条计数。

## 第五部分　完整实现流程（里程碑）

> 原则：**主干两件事先跑通，情绪与人设贯穿始终，锦上添花的往后放。** 每个里程碑给出目标、关键任务、验收标准。

### 阶段 0　设计冻结与准备（约 1 周）
- 产出：人设文档（名字/性格/语气/背景/红线）、30~50 组好坏对话对照集、隐私政策与权限文案草稿、UI 线框（三屏）。
- 工程：确定 LLM 供应商与 Key 方案；注册 `LlmClient` 协议；补齐 libs.versions.toml（网络客户端、WorkManager）。
- 验收：人设文档评审通过；好坏对话集入库。

### 阶段 1　消息采集真机闭环（主干②地基，部分已有）
- 任务：真机验证微信/QQ 通知解析；通知使用权引导；P0~P3 列表与反馈；分类 reason 展示。
- 验收：两台以上真机收到微信消息后 10 秒内正确入列表、分级正确；反馈后分类可变化。

### 阶段 2　AI 对话内核（主干①地基）★
- 任务：`LlmClient`（OpenAI 兼容 + SSE 流式）；人设宪法 prompt；聊天窗 UI（气泡、流式、按日期查阅历史）；本地会话存储；回复整形层；情绪初判（关键词版）。
- 验收：能连续对话；**红线测试集全部通过**（不回长文、不替用户想问题、崩溃场景先共情）；断网有兜底。

### 阶段 3　记忆与时序感知（亮点）★
- 任务：MemoryItem 表；LLM 记忆抽取（function calling）；夜间状态流转任务；上下文组装注入；"昨日复盘"触点。
- 验收：告诉 AI"明天下午三点有组会"，后天再问，AI 知道组会已结束；过期事件不再被当作未来日程提及。

### 阶段 4　主动陪伴与情绪疏导
- 任务：WorkManager 主动消息引擎；规则表（日程前/P0/早安晚安/长时未互动）+ 频率熔断；Soothing 模式对话流；危机词识别与热线提示。
- 验收：日程前 10 分钟收到一条"人话"提醒；模拟崩溃输入时 AI 不讲道理只陪伴；主动消息每日不超限。

### 阶段 5　日历与管家（主干②成型）★
- 任务：日历权限与系统日历同步；课程表模板；日程/待办本地库与日历屏；消息→待办抽取与确认卡片；冲突检测与提醒策略。
- 验收：导入课表后周视图正确；对 AI 说"下周三交论文"生成日程待确认；P0 微信群通知能抽出待办建议。

### 阶段 6　专注：CTDP 预约链 + 番茄
- 任务：预约倒计时、番茄钟、通知静默、链条计数、中断判例法对话、落座信号（按钮 MVP）。
- 验收：无力开始场景下，两次点击内完成"预约"；番茄期间 P3 通知不响；中断时出现"清零/例外"二选一。

### 阶段 7　主页与形象包装
- 任务：主页立绘 + 表情差分 + 实时时钟 + 昼夜状态；对话与专注状态联动；触控反馈。
- 验收：三屏导航完整；形象状态随时间/对话/专注正确切换。

### 阶段 8　合规、打磨与 demo
- 任务：权限引导全链路、数据导出/清除、云端开关与脱敏管道验证、真机矩阵适配、隐私政策；AstrBot 服务端对接（可选演示）；演示脚本（围绕"崩溃→被接住→预约→开始→消息被整理→第二天她记得"的故事线）。
- 验收：5 台真机回归通过；连续使用 7 天记忆/日程无错乱；demo 故事线彩排通过。

### 远期（锦上添花，不进本次承诺）
Live2D 形象、语音（TTS/ASR）、蓝牙/NFC/地理围栏落座、AstrBot 插件生态接入、Ollama 私域模型、RSIP 防摆烂协议探索、共场功能（明确不做）。
